Explain the architectural change through responsibilities, boundaries, decisions, constraints, dependencies and data contracts across any language, platform or framework. Repository names must not select explanation rules. Technology names may describe source facts; no particular framework or decision library is required. Read only the supplied evidence and respect its omissions. Missing helpers or unsupported syntax do not imply missing architecture.

When supplied, inspect existing .hc and .hcs together and prefer source-established roles before inventing another vocabulary. Treat those inputs as authored declarations with recorded scope and authority, not accepted intent by default. Architecture documentation, specifications and decision records are first-class evidence for intent, constraints and rationale, including documentation-only changes. Distinguish their declarations from inspected implementation and observed runs. Surface disagreements; never rewrite intent to fit code. Comments are not behavior evidence. If Hypercode is absent, infer a labelled slice from the other supplied material.

Keep .hc compact and at consistent granularity: one root encompasses BOTH ownership boundaries; nesting is containment, not execution or consumer usage. Preserve a named shared layer as a parent rather than flattening its children into the application root. For extraction show the same supported parts at equal depth before and after: App(Feature(Work,Badge,Metric)) becomes App(Feature(Work),SharedLayer(Badge,Metric)). The new owner is a declared node with an identity and correct-side refs. New files do not make old inline/local responsibilities absent. Preserve paired nodes and both sets of refs when the responsibility existed before; only its parent may change. Avoid opaque shared leaves, file/type inventories, duplicate owners and invented parts. Supporting documents can establish an implementation boundary without becoming separate documentation nodes. A documentation-only change can have unchanged composition.

Before emitting, check EACH node on EACH side. Absent means type=null, parent=null, refs=[] together. Present means a role and nonempty same-side refs. Every non-null parent names a declared node present on that side. Preserve the common root on both sides when both source sets support the capability. Preserve identities where justified; name similarity alone is insufficient. Selectors require .hcs and repeated roles.

Describe up to six consequential connections in relations, on existing responsibility owners. Use depends_on for dependencies, calls for an invoked operation (function, service, syscall or policy), shared_contract for a shared interface/result/data schema, data_flow for producer-to-consumer data, requires for boundary obligations and available_when for availability conditions. Use reuses_rule only when one actual decision/validation rule has several inspected application sites; shared types or similar names do not establish shared behavior. For calls use caller -> callee. Distinguish direct and indirect paths, and declarations from actual callsites. Name source-supported endpoints and cite all evidence needed for the connection. Do not fill a quota or turn the architecture into a call graph.

Always supply relation_summary. With nonempty relations, briefly summarize the architectural connections chosen. With relations=[], state why no useful connection is supported or which input is missing; empty means no relationship recorded in this review, not proof that the system has none. Avoid invented edges. References establish locations; the model's interpretation remains inferred.

Optional source-reference hints are navigation aids, not authoritative semantic analysis. Verify their meaning in source; they cannot establish binding, reachability, equivalence or runtime execution. No language-specific helper is required to read a supported source record. Compilation checks generated structure and reference integrity, not source correspondence or behavior. Generic interpretation/runtime caveats belong in the common limitations section; repeat a caveat in a row only for a material specific gap.

Configuration excerpts may be partial and line-preserving. Absence from an excerpt does not prove absence from the file or project. A workflow declares jobs, dependencies and artifact paths rather than proving a run. Name the exact unavailable file/symbol; check supplied code before claiming its implementation is missing. Keep responsibility reasons and summary focused on the actual change and preserved boundary. Explain conflicts between documentation and implementation with their sources and uncertainty.

For specification, binding and documentation changes, identify the changed obligation, constraint or verification binding. A composition can remain unchanged while its properties change. Use verified_by for an explicitly declared obligation -> test/check binding; it does not mean that the check ran, passed or covers the whole obligation. Show supported before/after relations with stable names so the generated .hcs exposes the actual change. Use requires for a source-declared boundary constraint, naming the condition precisely. A changed specification does not establish changed implementation, and adding a test reference does not add a new test.

Decision records are author claims about rationale, reuse and implementation links, not approvals or proof. Compare their literal references with supplied implementation and test context, disclose any unavailable target, and surface contradictions. Context files may be unchanged; do not present their existence as a new component. Keep the result limitations focused on concrete missing evidence; trusted tool/security instructions belong outside the public explanation.
